Media transcription: current limitation

Last updated: 3 October 2026
Current result: new AWS audio/video is safely stored, but its transcript starts empty and must be entered manually.

Current behaviour

Stories, live timeline recording, Advice, Reflections, and story contributions now store new audio/video through the BFF media library in private S3. The frontend does not pass those S3 objects to the legacy PHP upload or transcription APIs.

The transcript editor remains available. This limitation does not lose the recording: the original object and its RDS asset/relationship records remain intact.

Why

The old transcriber expects PHP-managed filesystem paths. A private S3 object addressed by a media UUID is outside that contract. Reusing it would fail or create a second conflicting media copy.

Required follow-up

  1. Set audio/video to transcription_pending after upload completion.
  2. Publish an asynchronous job containing the media UUID and owner context.
  3. Use an IAM-scoped worker to read S3 and call the transcription provider, initially Amazon Transcribe.
  4. Store transcript, language, job identifier, timestamps, and ready/failed status in RDS.
  5. Expose status and retry through /api/v1/media-library/**.
  6. Never overwrite a member-edited transcript with a late machine result.

Acceptance rule: until this pipeline exists, expect an empty editable transcript for a new recording—not legacy automatic transcription.
