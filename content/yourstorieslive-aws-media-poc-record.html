Independent media · Cloud deployment · POC findings

Our media.
Our AWS experiment.

We built a separate media path through NestJS, PostgreSQL and private S3, then hosted the current Next.js application and BFF in AWS. This record captures what we tried, what the evidence supports, and what needs another iteration.

PHP authentication preservedStandalone media databaseInfrastructure fully removed

9 October 2026 · Asia/Singapore · Source code and feature branches retained

Speaker notesThis POC asked whether we could take ownership of media without asking the PHP team to change its APIs or giving our database a connection to theirs. We also exercised hosting and deployment in AWS. The cloud environment has now been completely removed at the owner's request. This is a historical record, not an invitation to open the old testing URLs or a production launch announcement.

Speaker notesCloudFront sent API paths to the BFF and other paths to Next.js. The ALB kept a stable endpoint when tasks changed. This design provided a global entry point, not a multi-region application or database.

04 · Identity and persistence

Two tables.
One stable user identity.

media_library_assets

One row per uploaded asset.

  • owner_external_user_id: authenticated PHP user ID
  • public_id: UUID exposed by the API
  • id: internal BIGINT primary key
  • S3 keys, filename, MIME type and byte size
  • Captions, dates, dimensions, processing/deletion state

media_library_relationships

Connections between an asset and another application record.

  • media_asset_id: foreign key to our asset table
  • context_type: story, contact, profile, share, etc.
  • external_reference_id: business-record reference
  • recipient_external_user_id: share recipient
  • No foreign key or connection into the PHP database
PHP user ID → asset owner → asset internal ID → relationship → external record ID
                           └─ S3 original / generated thumbnail key

users/<owner-ID-hash>/original/<media-UUID>/<sanitized-filename>

Storage hashing organizes objects; authorization comes from BFF checks, IAM and private signed access. Month grouping falls back to upload date when a taken date is absent.

Speaker notesThere was no mirrored users table. Uploading created a media row containing the signed-in user's external ID. Relationships supported ten contexts: story, timeline, contact, profile, advice, reflection, moment, comment, contribution and share. Your Life used the shared user-liking integration. A supplied story or contact ID still needs permission and existence checks; storing a reference alone does not prove access.

Expand: example SQL joining Alex's story to its media
SELECT a.public_id, a.original_filename, a.storage_key
FROM media_library_relationships AS r
JOIN media_library_assets AS a ON a.id = r.media_asset_id
WHERE r.owner_external_user_id = '1001'
  AND r.context_type = 'story'
  AND r.external_reference_id = '501'
  AND r.deleted_at IS NULL
  AND a.owner_external_user_id = '1001'
  AND a.status = 'ready'
  AND a.deleted_at IS NULL;
Detach ≠ deleteRemoving a connection can mark only that link deleted. Deleting the media asset is a separate operation affecting its connected records and S3 objects.

The BFF maps internal rows to API UUIDs and signs authorized S3 reads. The browser receives neither internal join IDs nor database credentials. No sample has been inserted into AWS.

Speaker notesThe session identity anchors each lookup. The page adds a context type and external record ID. A recipient lookup follows share rows rather than changing the asset owner. The SQL example is an illustrative owner/story query, not a new database command we executed. More detail and the full field projections are included in the Markdown companion.

Speaker notesUploads used a single signed PUT per file. The multipart cleanup lifecycle rule should not be confused with an implemented browser multipart-upload protocol. A ready upload did not mean the video had been transcoded.

09 · Problems we encountered

What testing
made visible.

S3 images rejected by Next.js

Signed bucket URLs were outside the image allowlist. The feature configuration added Singapore S3 URLs under the user object path.

Video appeared as a broken image

MP4 bytes reached the image optimizer. Videos without posters now use a native video preview in the gallery.

New uploads grouped as “Undated”

Gallery queries now fall back to the upload timestamp when no captured date is recorded.

Live recording upload returned 422

Recorder MIME values included codec parameters. The upload client normalizes the MIME value sent to the API.

Hosted image loading felt slow

User reported roughly 4–7 seconds versus faster localhost. We tried image derivatives, hosting capacity and CloudFront delivery; no final benchmark proved a latency target.

Pausing left costs behind

ALB/public IPs and stored data still cost money. Full removal needed explicit cleanup of retained storage, images and logs.

Speaker notesThese findings led to concrete code and operational changes. Do not translate them into a claim that every playback problem was fixed. Native video previews still fetch metadata and can be expensive in a grid. S3 signatures can change optimizer cache keys, and global edge delivery cannot remove server image-conversion work or reduce original video bitrates.

10 · Media limitations

Playback works.
A video pipeline is still needed.

AreaPOC behaviorNext work
Image processingSharp generates 600 × 600-bounded WebP thumbnails.Resource limits, isolation and acceptance tests.
Video optimizationOriginal uploaded video; native browser player.Poster generation, compatible codecs, fast-start and measured bitrate needs.
Byte rangesS3 supports range GET; direct signed playback.Capture actual 206 responses and test seek/startup.
URL expiry / retry15-minute URLs; no automatic renewal. Retry adds a query parameter.Request a fresh authorized URL; preserve playback position.
Share revocationStops issuing fresh URLs; existing URLs can survive to expiry.Define acceptable revocation delay and viewer access policy.
TranscriptsManual editable text; new recordings do not call PHP transcriber.Independent asynchronous transcription pipeline.

No HLS/DASH, video transcoding, generated video posters, fast-start conversion or Transcribe service was deployed.

Speaker notesS3 byte-range delivery is useful but is not adaptive streaming. Browser codec compatibility and video layout still matter. The signed URL is a temporary bearer credential: anyone holding it can use it until expiry. Changing its query string can invalidate the signature, so retry should ask the BFF for a new URL rather than modify the old one. These were known gaps at closure, not changes implemented by this report.

12 · Cost and production lessons

Small compute.
Persistent baseline costs.

~$113Historical active month
~$30Historical paused month
1 / 2Frontend vCPU / GiB

Planning, not an invoice

Earlier guides estimated US$112–114/month for both services always running with light usage. Five deployed secrets should replace the older estimate's count of four.

Pause is not delete

Task and DB compute stopped, while ALB/IPs, storage and secrets remained. A stopped RDS instance automatically restarts after seven days.

Production needs another pass

Multi-AZ decisions, longer backup retention, deletion protection, restore tests, migrations, TLS to origin and target authorization were still needed.

Fargate sizing1 vCPU / 1 GiB is unsupported. Keeping 1 vCPU meant retaining at least 2 GiB. The POC stayed at 1 vCPU / 2 GiB.

Historical Singapore estimates assume approximately 730 hours/month. Re-price a future design for current rates, traffic, credits and retention.

Speaker notesThese numbers explain the decisions made during the POC; they are not a bill or a new pricing quote. Small test workloads can spend a meaningful proportion on a load balancer and public IPs. CloudFront's distribution did not have an hourly charge but delivery is usage-based. Turning off compute leaves those fixed or stored-resource costs, which is why the final instruction was complete teardown.

14 · Next iteration

Carry forward the boundary.
Prove the remaining journeys.

1 · Make playback resilient

Fix URL renewal and retry, verify range requests, add video posters and compatible playback derivatives, then benchmark representative uploads.

2 · Make relationships reliable

Verify external-record access and save/link consistency. Test two-user sharing, revocation and contribution/invitation journeys.

3 · Choose the next infrastructure

Compare a simpler POC host with ECS/ALB using current prices. Set retention, versioned migrations, restore targets and HTTPS before production.

4 · Add processing and migration

Separate processing capacity as volume grows; add independent transcription. Run reviewed legacy inventory/copy/reconciliation before bulk migration.
