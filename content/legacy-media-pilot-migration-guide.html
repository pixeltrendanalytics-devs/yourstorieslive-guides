Legacy media inventory and pilot import

A safe, read-first process for discovering and copying one existing user's legacy media into the new BFF, private S3 bucket, and RDS media database—without changing PHP or touching its database.

Core rule: inventory first, approve an exact manifest hash, then copy only the approved URLs. The legacy system remains untouched and authoritative throughout the pilot.

1. Architecture at a glance

1. AuthenticateSign in as one authorized existing user and verify logged_in_user_id.
2. InventoryCall bounded compatibility read APIs. Normalize assets, metadata, and relationships.
3. ApproveReview counts and exceptions. Approve the immutable manifest SHA-256.
4. Pilot importFetch exact approved URLs and write only through new BFF media APIs.
5. ReconcileCompare bytes, metadata, relationships, UI behavior, and authorization.
Legacy trust zone
Authenticated compatibility reads → PHP backend → exact media URL. No mutations and no directory crawling.
Operator zone
Protected manifest, approval, mapping, exceptions, and reconciliation. No tokens or media blobs in Git.
New media zone
BFF upload/metadata/relationship APIs → private S3 + RDS. Browsers receive short-lived signed URLs only.

2. Scope and safety

Included in the pilot

  • One explicitly selected user per run.
  • Media visible through authenticated reads.
  • Images, videos, audio, metadata, and exposed relationships.
  • Story/timeline, contacts, contributions, profile, advice, reflections, moments, and shares when identities are available.
  • Restartable copy into private S3 and new RDS records via BFF.

Not included

  • No direct PHP database access or writes.
  • No changes to PHP code or files.
  • No recursive crawl of /resources/.
  • No guessed ownership or relationship target IDs.
  • No deletion/replacement of legacy assets.
  • No bulk-user migration or production cutover.
Security note: the Apache listing under legacy.example.invalid/resources/ exposes storage structure. Ask PHP operations to disable directory indexing separately. Do not use that listing as a migration source or as evidence of ownership.

4. Tool two: legacy-media-pilot-import

CONTROLLED WRITES Dry-run is the default. Execution requires an explicit flag.

Per-item execution

  1. Verify manifest hash, approval record, authenticated user, item/byte limits, and host allowlists.
  2. Read the prior mapping checkpoint; skip reconciled items or resume the next incomplete state.
  3. GET only the exact approved source URL and stream the body.
  4. Enforce status, byte limit, MIME detection, reported size, and calculate SHA-256.
  5. Create an upload intent with the new BFF.
  6. Stream to the returned short-lived signed S3 PUT URL.
  7. Complete the upload through BFF so it verifies and persists the media record.
  8. Apply supported metadata through BFF APIs.
  9. Create supported relationships through BFF APIs.
  10. Atomically checkpoint after every durable step.
  11. Read back the new asset and mark it reconciled only after comparison succeeds.

Restartable states

discoveredapprovedsource_verifiedupload_createdobject_uploadedcompletedmetadata_appliedrelationships_appliedreconciled

Any operational step may enter retryable_error. Retry resumes from the checkpoint. An ownership, identity, checksum, or mapping conflict is terminal until reviewed.

Idempotency identity

SHA-256(source_system + source_table + legacy_record_id + legacy_user_id)

The new mutation endpoint should enforce that idempotency key before bulk migration. The pilot mapping reduces duplication risk, but a local file alone cannot fully cover a lost network response.

5. Protected pilot mapping

The pilot uses mapping.json outside Git. It stores operational progress—not credentials, cookies, signed URLs, response headers, or media bytes.

{
  "schemaVersion": 1,
  "sourceSystem": "ysl-legacy-php",
  "legacyUserId": "2123",
  "manifestSha256": "<approved-sha256>",
  "items": {
    "photo_gallery:88421": {
      "sourceSha256": "<content-sha256>",
      "newMediaId": "0b1f5dc1-5caa-4bf3-85c5-7405c2e5ae39",
      "state": "reconciled",
      "completedRelationships": ["story:991"],
      "attempts": 1,
      "lastError": null,
      "updatedAt": "2026-10-04T09:12:00Z"
    }
  }
}
  • Key by source table/module plus legacy record ID—not filename or URL.
  • Write to a sibling temp file, flush, then atomically rename.
  • Keep one previous valid copy for recovery.
  • A changed content checksum is a conflict, not an automatic overwrite.

6. Production mapping in RDS

Before multi-user migration, create legacy_media_mappings. The unique identity is (source_system, source_table, legacy_record_id). Recommended fields:

GroupColumns
Identityid, source_system, source_table, legacy_record_id, legacy_user_id
New recordmedia_asset_id foreign key to the canonical media asset
Integritymanifest_sha256, source_url_hash, source_content_sha256
Progressmigration_state, completed_relationships, attempt_count
OperationsRedacted error code/detail, first seen, last attempt, reconciled, created, updated timestamps

Index (legacy_user_id, migration_state) and media_asset_id. Restrict access to the migration service role. This table is for audit/idempotency; normal media tables remain canonical.

8. Transcript limitation

The legacy API may return transcript text, but the new media model does not yet have a durable transcript target. Preserve it in the protected manifest and report it as pending_target_support. Do not drop or regenerate it. Before bulk migration, add a BFF-managed transcript table/API and then import it.

9. Failure behavior

ConditionAction
Stopped after S3 uploadRead recorded state and resume; do not create a second asset blindly.
Lost completion responseRead status before retrying completion.
Relationship failureKeep the asset and retry only the missing link.
Legacy 403/404Record exception; never guess a path.
MIME/checksum conflictStop and require review.
New BFF 401/403Stop the whole run.
Transient 429/5xxCapped exponential backoff with jitter.
Different new ID already mappedStop as an idempotency conflict.

10. Reconciliation

Automated

  • Discovered = imported + excluded + failed + deferred.
  • One stable legacy identity → exactly one new asset.
  • Checksum/size/MIME and supported metadata match.
  • Every supported relationship exists once.
  • No asset is owned by another user.
  • Every unsupported field has a reason.

Manual

  • Compare gallery samples with the legacy UI.
  • Open image, video, and audio.
  • Check captions, dates, and linked feature pages.
  • Test reuse of migrated gallery assets.
  • Verify cross-user denial and signed-URL expiry.
  • Verify the S3 bucket is private.

11. Pilot runbook

  1. Prepare: choose an authorized existing test user; create protected storage; configure identity, hosts, item limits, and byte budget.
  2. Inventory: run bounded reads; validate the user ID; review summary, exceptions, and visual samples.
  3. Approve: record approval against the exact manifest hash.
  4. Dry run: show intended assets, relationships, bytes, unsupported fields, and deferrals without writing.
  5. Execute small: concurrency 1; prove one image, one video, and one audio asset first.
  6. Expand carefully: add metadata and relationship domains incrementally.
  7. Reconcile: generate automated results and verify UI/authorization.
  8. Close: preserve protected audit files; keep legacy data unchanged; translate findings into bulk-migration requirements.

12. Rollback and future cutover

The pilot is additive. Keep PHP media unchanged. Run on an isolated or feature-flagged user. If cleanup is required, remove only new records through supported BFF delete APIs and keep the audit mapping. A future production cutover needs server-side per-user state:

legacy_only → inventory_ready → import_in_progress → verification_required → new_media_enabled

Only reconciliation permits new_media_enabled. Failure leaves the user on the legacy path.

13. Go/no-go checklist

  • ☐ Authorized test account selected
  • ☐ Authenticated ID equals manifest user
  • ☐ Read endpoints are bounded
  • ☐ Hosts and paths are allowlisted
  • ☐ Exact manifest hash approved
  • ☐ No secrets/signed URLs/media in Git
  • ☐ New writes are idempotent/restartable
  • ☐ S3 is private
  • ☐ Mapping storage is protected
  • ☐ Reconciliation is ready
  • ☐ Cross-user authorization test is ready
  • ☐ Legacy media remains untouched

Bulk migration is a separate project requiring the RDS mapping table, controlled workers, monitoring, rate limits, per-user cutover state, and an authorized source-data strategy.
